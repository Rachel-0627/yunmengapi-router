# 部署指南

> 目标:在一台香港服务器上跑起 **营销站 + new-api 网关**,全程约 1 小时。
> 配置文件都在 `deploy/`,基本是复制粘贴。

## 架构

```
              ┌─────────── Caddy (80/443,自动 HTTPS) ───────────┐
              │                                                  │
  yunmengapi.com          console.yunmengapi.com     api.yunmengapi.com
       ↓                          ↓                          ↓
  web:3001 (营销站)          new-api:3000            new-api:3000
                                  ↓
                    postgres + redis(内网,不对外开放端口)
```

**为什么拆子域名:** new-api 自身占用了 `/`、`/pricing`、`/models`、`/register` 等路径,
与营销站直接冲突。按子域名切分最干净,也是行业通行做法。

---

## 一、买服务器

香港节点,**2核2G / 40G 硬盘**起步。系统选 **Ubuntu 24.04**。

装好后先做基础加固:

```bash
# 只放行 SSH 与 HTTPS
ufw allow 22/tcp && ufw allow 80/tcp && ufw allow 443/tcp
ufw --force enable

# 禁止 root 密码登录(改用密钥)
sed -i 's/^#\?PermitRootLogin.*/PermitRootLogin prohibit-password/' /etc/ssh/sshd_config
sed -i 's/^#\?PasswordAuthentication.*/PasswordAuthentication no/' /etc/ssh/sshd_config
systemctl restart ssh
```

装 Docker:

```bash
curl -fsSL https://get.docker.com | sh
```

## 二、配 DNS

在 Porkbun 后台,给域名加三条 **A 记录**,全部指向服务器 IP:

| 主机名 | 类型 | 值 |
|---|---|---|
| `@` | A | 服务器 IP |
| `www` | A | 服务器 IP |
| `console` | A | 服务器 IP |
| `api` | A | 服务器 IP |

> Caddy 申请证书需要域名已经解析到位,**先配 DNS 再启动服务**。

## 三、放代码

```bash
mkdir -p /opt/yunmeng && cd /opt/yunmeng
# 把本仓库(web/ 和 deploy/)传上来
```

### 校验镜像签名(可选但推荐)

new-api 使用官方镜像,但**按 sha256 摘要锁定**,并且该镜像由 GitHub Actions
自动构建 + cosign keyless 签名。可以这样验证它确实来自该仓库的工作流:

```bash
# 装 cosign
curl -sLO https://github.com/sigstore/cosign/releases/latest/download/cosign-linux-amd64
sudo install cosign-linux-amd64 /usr/local/bin/cosign

# 验证签名来源
cosign verify \
  --certificate-identity-regexp 'https://github.com/QuantumNous/new-api/.github/workflows/.*' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  calciumion/new-api@sha256:54a0b10924aa75fa5b5947208b820ced66b6ef4b445b35f122b31d80676aba2b
```

验证通过 = 密码学证明这个镜像由 QuantumNous/new-api 仓库的 CI 构建,
不是任何人手工打包的。**这比自行编译提供的保证更强** —— 自己编译只能证明
"我用这份源码编的",而签名能证明"官方 CI 用打了 tag 的源码编的"。

## 四、生成密码

```bash
cd /opt/yunmeng/deploy
cp .env.example .env
bash gen-secrets.sh        # 自动生成 4 个随机强密码,并把 .env 设为 600
```

**绝不要手写密码,也绝不要用官方示例里的 `123456`。**

## 四点二、⚠️ 绝不要在服务器上构建

**实测教训:这台 2 核 1.6G 的机器跑不动任何 Docker 构建。**

| 尝试 | 结果 |
|---|---|
| 在服务器编译 new-api(12 万行 Go) | SSH 失联 25 分钟仍未完成,只能强制重启 |
| 在服务器构建 Next.js(npm ci + build) | 同样失联,再次强制重启 |
| **改为本地构建 + 只传成品** | **5.4 秒完成** |

因此:

- **new-api** 用官方签名镜像,不编译
- **营销站**在开发机上构建,只把 `.next/standalone` 成品传上去

改了前端代码要重新部署时:

```bash
# 在开发机上
bash deploy/build-web.sh                    # 构建并生成 web/.deploy-bundle
rsync -az --delete -e "ssh -i ~/.ssh/yunmeng_deploy" \
  web/.deploy-bundle/ admin@服务器IP:/opt/yunmeng/web/.deploy-bundle/

# 在服务器上
cd /opt/yunmeng/deploy && sudo docker compose up -d --build web
```

## 四点五、加 swap(2GB 机器必做)

构建 Next.js 时峰值内存约 1.4GB,加上系统和 Docker 守护进程,2GB 机器很容易
在构建阶段被 OOM 杀掉。先加 2GB swap 兜底:

```bash
fallocate -l 2G /swapfile
chmod 600 /swapfile
mkswap /swapfile && swapon /swapfile
echo '/swapfile none swap sw 0 0' >> /etc/fstab   # 重启后仍生效
free -h                                            # 确认 Swap 那行有 2.0Gi
```

> swap 只在构建时用得上,日常运行常驻内存约 730MB,不会碰到它。

## 五、启动

```bash

docker compose ps                  # 五个容器都应是 running/healthy

```

访问 `https://console.yunmengapi.com` —— **第一个注册的账号自动成为管理员**,请立刻注册占位。

```bash

  echo '0 4 * * * /opt/yunmeng/deploy/backup.sh >> /var/log/yunmeng-backup.log 2>&1' ) | crontab -

sudo touch /var/log/yunmeng-backup.log && sudo chown admin:admin /var/log/yunmeng-backup.log

```

+ `docker-compose.yml` + `Caddyfile`。

## 加固清单(已在配置里落实)

| 措施 | 解决什么 |
|---|---|
| **镜像按 sha256 摘要锁定** | 内容一旦被替换,拉取会直接失败。不用 `:latest`(那个标签会被自动覆盖) |
| **镜像有 cosign 签名 + SLSA 溯源 + SBOM** | 可密码学验证构建来源就是官方 CI 工作流 |
| **密码全部随机生成,存 `.env`(权限 600,已 gitignore)** | 仓库里没有任何明文密码 |
| **postgres / redis 不映射任何主机端口** | 数据库无法从公网触达 |
| **new-api 与 web 只 `expose`,不 `ports`** | 只能经 Caddy 访问 |
| **`backend` 网络设为 `internal`** | 数据层与外网物理隔离 |
| **Caddy 自动 HTTPS + HSTS 等安全响应头** | 传输加密,基础防护 |
| **ufw 只放行 22/80/443** | 攻击面最小 |
| **容器以非 root 用户运行(营销站)** | 逃逸后权限受限 |
| **日志按 10MB × 3 轮转** | 不会写爆磁盘 |
| **每日自动备份,保留 14 天** | 出事能回滚 |

## 升级 new-api 的正确姿势

```bash
cd /opt/yunmeng/deploy/new-api
git fetch --tags
git log --oneline v1.0.0-rc.25..<新版本>   # 先看改了什么
git checkout <新版本>

```

**不要用 `latest`,不要盲目升级。** 升级前先备份。

## 附:从境外访问发卡平台(catfk.com)

**现象:** 你的电脑和手机打不开 `catfk.com`,报 `ERR_CONNECTION_RESET`;
但中国大陆能正常访问下单。

**原因:** catfk.com 挂在中国的 CDN「爱云防护」(`aiyunfanghu.cn`)后面,
源站 IP `211.154.31.104` 在中国大陆。该 CDN 对远距离境外 IP 直接发 RST 重置。

已排除的可能:
- ❌ 站点故障 —— 香港服务器同一时刻访问返回 200,JS 资源全部正常加载
- ❌ 地域 DNS 分流 —— 境内外解析到的是同一个 IP
- ❌ 链接配置错误 —— 数据库里 `TopUpLink` 值干净无误

**影响:** 客户(中国大陆)不受影响,能正常购买。只有你自己管不了店铺后台。

**解法:** 借用你自己的香港服务器做 SOCKS5 跳板。

```bash
# 启动(-f 自动转后台,不用一直开着窗口)
ssh -i ~/.ssh/yunmeng_deploy -f -N -D 1080 admin@47.76.40.132

# 验证
curl --socks5-hostname 127.0.0.1:1080 -o /dev/null -w "%{http_code}\n" \
  https://catfk.com/shop/ZL8E2CDF     # 应返回 200

# 关闭
pkill -f "ssh.*-D 1080"
```

浏览器设 SOCKS5 代理 `127.0.0.1:1080` 即可访问。
**推荐用 SwitchyOmega 插件做分流**,只让 catfk.com 走代理,其他网站直连。
