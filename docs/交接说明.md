## 一、这是什么项目

**云梦API(yunmengapi.com)** —— 一个面向**中国大陆开发者**的 AI API 中转站。

商业模式:从上游中转站 `zexitongxue.com` 批发购买模型额度,加价转售给国内开发者。客户把自己程序里的 `base_url` 换成我们的地址,就能用上 Claude / GPT 等模型,价格比官方便宜。

**运营者背景**:非专业工程背景,全部依靠 AI 辅助开发。规模很小、短期运营、不涉及大额资金。

### 明确的经营约束(不可违反)

- **不做任何赠送**:充多少钱用多少钱,无注册赠额、无充值返利、无折扣分组
- **不上架免费模型**:不放任何可供"薅羊毛"的产品和功能
- **不修改 new-api 源码**:AGPL 协议 + 每次升级都要重打补丁 + 服务器无法编译
- **Git 提交纪律**:commit message 和 commit author 中**不得出现任何 AI 助手品牌关键词**

## 七、必须知道的技术要点(踩坑总结)

### 计费公式

```
按 Token:  quota = (新输入 + 缓存读×0.1 + 缓存写×1.25 + 输出×5) × 模型倍率 × 分组倍率
按次固定:  quota = 模型固定价格 × QuotaPerUnit × 分组倍率 × 其他倍率(如图片张数 n、视频秒数)
```

- `QuotaPerUnit = 500000`
- **单价(¥/1M token) = 2 × 模型倍率 × 分组倍率**
- 后台「模型定价」表单直接填**价格**,换算见 `vendor/new-api/web/src/features/system-settings/models/model-pricing-core.ts:162`(`价格 = 倍率 × 2`)
- 表单标注的「$」是 new-api 上游的默认假设,**在本站单位等同人民币**,填 `2.1` 就是 ¥2.10/1M

### 计费用的是客户请求的模型名

`vendor/new-api/relay/helper/price.go:74` —— `GetModelPrice(info.OriginModelName)`。
**模型映射只改发给上游的名字,不影响计费。** 因此可以用两个对外模型名 + 映射,实现"同一上游模型卖两种价"(生图 1K/4K 就是这么做的)。

映射格式(`vendor/new-api/relay/helper/model_mapped.go:28-33` 已验证):
```json
{"客户请求的名": "发给上游的名"}
```

### 模型价格未配置会直接拒绝请求

`price.go:74` 找不到价格 → `usePrice=false` → 退回按 token 计费;若模型倍率也没有 → **HTTP 400「模型 X 的价格未配置」**。
模型广场里显示的价格可能是**内置默认值**,不代表真的配好了 —— 曾出现 gpt-5.4 在广场标价 ¥75 但一调用就 400。

### 渠道类型决定能力,不能乱改

- `New API`(类型 60):支持 OpenAI / OpenAIResponse / Anthropic / Gemini / AlphaSearch 五种端点,**这是对接上游中转站的正确选择**
- `自定义`(类型 8):`vendor/new-api/relay/channel/openai/adaptor.go:169-172` 把 API 地址当作完整请求地址原样发出,不拼 `/v1/chat/completions` → 404;且退化成纯 OpenAI 端点,失去 Anthropic 原生支持
- **视频任务**:`vendor/new-api/relay/relay_adaptor.go:144-173` 的 `GetTaskAdaptor` **没有 `New API` 分支**,返回 nil。视频必须新建 `Sora`(类型 55)类型渠道

### 生图模型不按尺寸区分价格

`vendor/new-api/relaykit/dto/openai_image.go:137` —— `sizeRatio` 只对 `dall-e` 前缀生效,`gpt-image-2` 恒为 1。
**所以 1K/4K 差价必须靠两个模型名实现,不能靠 size 参数。**

### new-api 不认识 gpt-image-2

`vendor/new-api/common/model.go:12-19` 的 `ImageGenerationModels` 只有 `dall-e-3` `dall-e-2` `gpt-image-1` `imagen-` `flux-`,而 `OpenAITextModels` 含 `gpt-`。
所以 `gpt-image-2` 被误判为**文本模型** → 渠道测试按钮会发聊天请求、必然失败。**这只影响测试按钮和能力标签展示,不影响真实请求路由**(按 URL 路径分发)。

### 内置文案改不了

`vendor/new-api/i18n/i18n.go:25-26` 用 `go:embed` 把语言文件编译进二进制,加载时只读内嵌副本,**挂载文件无效**。
例:注册重名提示「用户名已存在,或已注销」写在 `i18n/locales/zh-CN.yaml:74`,想改只能重新编译。

### 用户注销是软删除,用户名被永久占用

- 用户自己注销(`controller/user.go:991`)→ 软删除 → 用户名不可复用
- 管理员在后台删除(`controller/user.go:966`)→ **硬删除** → 用户名立即释放
- 后台用户列表用了 `tx.Unscoped()`(`model/user.go:402`),**能看到已注销账号**
- 硬删除会连带删除该用户所有令牌,但**消费日志会变成孤儿记录**

### 邮箱字段绑死在验证开关上

`controller/user.go:231-272`:`EmailVerificationEnabled` 关闭时,邮箱**既不保存也不参与查重**。
所以"收邮箱但不验证"做不到。当前未开验证 → **客户忘记密码会永久锁死**,只能管理员手动改。

## 八、当前卡住的三个问题(核心难点)

### 难点一:生图无法交付 —— 上游异步、new-api 只认同步

**现象**
```
POST /v1/images/generations  (model: gpt-image-2)
→ HTTP 202  {"success":true,"pending":true,"task_id":"aiimg_...","status":"queued","data":[]}
```

**new-api 侧的硬编码限制**(`vendor/new-api/relay/image_handler.go:100-105`):
```go
if httpResp.StatusCode != http.StatusOK {
    if httpResp.StatusCode == http.StatusCreated && info.ApiType == constant.APITypeReplicate {
        httpResp.StatusCode = http.StatusOK      // 只给 Replicate 的 201 开了口子
    } else {
        newAPIError = service.RelayErrorHandler(...)   // 其余一律判错
    }
}
```
**只接受 200,没有任何配置项能放行 202。**

**更致命的是上游没有轮询接口。** 已实测以下路径全部 404:
```
GET  /v1/images/generations/{id}
GET  /v1/tasks/{id}
GET  /v1/images/{id}
GET  /v1/task/{id}
GET  /v1/images/generations?id={id}
POST /v1/images/fetch
POST /v1/chat/completions  (用图模型) → 502
```

而 new-api 的 OpenAI 兼容路由下**没有通用任务查询端点** —— `vendor/new-api/router/relay-router.go` 里只有 `/mj`(Midjourney)和 `/suno` 有 fetch 路由。

**当前表现**:客户调用返回 `{"error":{"message":"openai_error","type":"bad_response_status_code"}}`。
**已验证不会乱扣钱**:连打两次失败请求,余额 `11.736554 → 11.736554` 分文未动,预扣额度被正常退回。

**结论:必须上游提供任务查询接口或同步模式,否则这条线做不了。**

### 难点二:视频时长参数不生效 —— 上游固定输出 12 秒

**好消息:整条链路技术上是通的。** 已端到端验证:
```
① POST /v1/videos              → 200 {"task_id":"task_...","object":"video","status":"queued"}
② GET  /v1/videos/{task_id}     → queued 20% → completed 100%
③ 完成响应带 url                → 下载得到 3.4MB / 4.5MB 的有效 MP4
```

且 new-api 的 sora 适配器打的正是同样两个路径:
```go
// vendor/new-api/relay/channel/task/sora/adaptor.go:136
return fmt.Sprintf("%s/v1/videos", a.baseURL)          // 提交
// :266
uri := fmt.Sprintf("%s/v1/videos/%s", baseUrl, taskID) // 轮询
```
new-api 的视频路由(`vendor/new-api/router/video-router.go`)也齐全:
```
POST /v1/videos                     → RelayTask
GET  /v1/videos/:task_id            → RelayTaskFetch
GET  /v1/video/generations/:task_id → RelayTaskFetch
GET  /videos/:task_id/content       → VideoProxy
```

**坏消息:上游忽略时长参数,固定生成 12 秒。** 四种写法全部复现:

| 请求 | 响应 seconds | 实测 MP4 时长 |
|---|---|---|
| `{"seconds":"5"}` 字符串 | `"12"` | **12.05 秒** |
| `{"seconds":"4"}` 字符串 | `"12"` | — |
| `{"duration":4}` 整数 | `"12"` | — |
| `{"seconds":5,"resolution":"480p","aspect_ratio":"16:9"}` **完全照抄官方文档示例** | `"12"` | **12.10 秒** |

而上游文档和价格页都明确写着「**支持 4–15 秒整数时长;按秒计费**」。**这是上游的 bug 或未公开的参数写法。**

**为什么会亏钱**:
```
new-api 按【客户请求的秒数】扣费(不填默认 4 秒)
上游按【实际生成的 12 秒】收我们钱

以 seedance-mini-2.0-480p(进货 ¥0.32/秒)、售价 ¥0.80/秒 计:
  客户请求 4 秒 → 收 4 × 0.80 = ¥3.20
  上游实际扣  → 付 12 × 0.32 = ¥3.84
                 ─────────────────
                 每单净亏 ¥0.64
```

### 难点三:视频完成响应不返回计费秒数 —— 无法差额结算

new-api 有完成后重新结算的机制,但**对视频这条路径失效**,两处原因:

```go
// vendor/new-api/service/task_polling.go:648-651
// 按次计费的任务不做差额结算
if bc := task.PrivateData.BillingContext; bc != nil && bc.PerCallBilling {
    logger.LogInfo(ctx, "任务按次计费,跳过差额结算"); return
}

// vendor/new-api/relay/channel/task/sora/adaptor.go:290-322  ParseTaskResult
// 只解析 status / progress / error,完全不回读实际 seconds
```

上游文档也确认:`GET /v1/videos/{task_id}` 的完成响应只有 `task_id` / `model` / `status` / `progress` / `download_url`,**不包含计费秒数**。

**所以"先按请求扣、完成后按实际补差"这条路也走不通。**
