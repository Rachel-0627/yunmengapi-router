# 求助:AI 中转站的生图接口异步/同步不兼容,找代价更小的方案

## 背景

我运营一个小型 AI API 中转站(转售上游中转站的模型额度)。

- **网关**:[QuantumNous/new-api](https://github.com/QuantumNous/new-api)(Go,AGPL-3.0),用官方 Docker 镜像 `calciumion/new-api:v1.0.0-rc.25`,digest 锁定
- **上游**:另一家中转站,也是 new-api 架构
- **部署**:Caddy + new-api + PostgreSQL + Redis,Docker Compose
- **服务器**:2 核 1.6G(实测在上面编译 Go 会把 SSH 打到失联,不可行)

**硬约束(不可协商):**

1. **不能修改 new-api 源码** —— AGPL 协议;每次升级要重打补丁;服务器编译不动;自行构建会失去官方镜像的 cosign 签名与 SLSA 溯源
2. 文本模型和视频模型都已正常运行,**只有生图不通**

## 问题:上游生图只有异步接口,new-api 只支持同步

### 上游的实际行为(全部实测过)

**① 标准路径 —— 返回 202 排队票,不是图**

```bash
POST https://<上游>/v1/images/generations
{"model":"gpt-image-2","prompt":"...","size":"1024x1024","n":1}

→ HTTP 202
{"success":true,"pending":true,"type":"image",
 "id":"aiimg_1788052945789_d8dcad2f","task_id":"aiimg_...",
 "status":"queued","progress":1,"data":[]}
```

**② 异步路径 —— 这条是通的**

```bash
POST https://<上游>/v1/images/generations/async     # 注意 /async 后缀
→ HTTP 200
{"id":"aiimg_...","task_id":"aiimg_...","status":"queued","progress":1,"data":[]}

GET https://<上游>/v1/images/tasks/{task_id}
→ HTTP 200,轮询约 100 秒
{"success":true,"pending":false,"type":"image","task_id":"aiimg_...",
 "status":"completed","progress":100,
 "url":"https://<上游>/ai/generated-media/gallery/20260830/xxx.png",
 "direct_url":"...","proxy_url":"...","b64_json":""}

GET <上面那个 url>
→ HTTP 200,image/png,1024×1024,约 1.1MB
```

**关键事实(已实测)**:
- 图片 URL **免鉴权可下载**(不带 Authorization 也返回 200)
- 上游文档说结果**保留约 2 小时**
- 该 Key 下 3 个生图模型(`gpt-image-2`、`gemini-3-pro-image-preview`、`gemini-3.1-flash-image-preview`)**全部只支持异步**,标准路径分别返回 202 / 500 / 500
- 上游文档原文:「客户对接**统一使用**主站 Bearer 鉴权异步接口:提交任务、轮询状态、鉴权下载结果」→ 这是**有意的架构设计**,不是 bug

### new-api 侧的限制(已查源码)

**① 图片中继只接受 HTTP 200,硬编码**

```go
// relay/image_handler.go:100-105
if httpResp.StatusCode != http.StatusOK {
    if httpResp.StatusCode == http.StatusCreated && info.ApiType == constant.APITypeReplicate {
        httpResp.StatusCode = http.StatusOK      // 只给 Replicate 的 201 开了口子
    } else {
        newAPIError = service.RelayErrorHandler(...)   // 其余一律判错
    }
}
```
没有任何配置项能放行 202。

**② 请求路径写死为标准路径**,不会加 `/async`。

**③ OpenAI 兼容路由下没有任务查询端点** —— `router/relay-router.go` 里只有 `/mj`(Midjourney)和 `/suno` 有 fetch 路由。所以即使客户拿到 task_id 也无处可查。

**④ 视频却是支持的**(说明 new-api 有异步能力,只是没给生图):
```go
// router/video-router.go
POST /v1/videos                     → RelayTask        提交
GET  /v1/videos/:task_id            → RelayTaskFetch   轮询
GET  /videos/:task_id/content       → VideoProxy       取文件
```
视频走 `Sora` 类型渠道 + `tasksora.TaskAdaptor`,已实测跑通。但 `GetTaskAdaptor`(`relay/relay_adaptor.go:144-173`)里**没有任何图片类的适配器**。

**当前客户看到的结果**:
```json
{"error":{"message":"openai_error","type":"bad_response_status_code",
          "code":"bad_response_status_code"}}
```
(好消息:失败时预扣额度会正常退回,已连续两次验证余额未变)

## 我目前想到的方案,以及它的代价

**加一个中间层容器**,对 new-api 伪装成同步生图 API:

```
客户 → new-api(鉴权+计费)→ 中间层 → 上游
                              ① POST /v1/images/generations/async
                              ② GET  /v1/images/tasks/{id} 轮询
                              ③ 返回 {"created":..,"data":[{"url":".."}]}
```

new-api 渠道的「API 地址」改指向 `http://image-shim:8080`,密钥仍由 new-api 透传,不用复制。

**已确认的可行性前提**:
- `RELAY_TIMEOUT=0`(new-api 不限时)
- Caddy `read_timeout 600s / write_timeout 600s`
- 生图约 100 秒,在超时范围内

**代价**:约 120 行代码 + 多一个容器 + 每次生图占用一条长连接约 100 秒 + 上游接口改版要跟着维护。
